# Performance and observability report

Status: measured on the live end-to-end run (session 037). Generated by `e2e/report.py`. Local machine, one user at a time, real model providers (free or entry tiers), Neon Postgres over the internet, mocks on localhost. Numbers show where time goes; they are not a capacity test.

## How it is measured

- **API latency:** the harness times every HTTP call it makes (what a user waits for).
- **Inside a turn:** `backend/app/observability.py` adds a LangChain callback to every graph run. It writes one JSON line per graph node, model call and tool call (`TRACE_LOG`: name, ms, status, model, tokens). The same runs go to LangSmith (project `claimwise`, run name `claimwise:<route>`, thread id in metadata) when `LANGSMITH_API_KEY` is set.

## Findings

- Most of the wait is not the model. A refresh (`GET /api/thread`) makes no model call and its graph nodes take milliseconds, yet it took about 6.7 s when measured alone: one round trip to the Neon database took 143 ms, and LangGraph writes a checkpoint after every node (about 6 to 11 per turn) plus reads the state back.
- Options, for the owner to decide (not changed here because they alter what survives a crash mid-turn): checkpoint once per turn (LangGraph `durability="exit"`; pauses are still saved), host the database in the same region as the API, or keep a warm connection pool sized for concurrent turns.
- Model latency is acceptable: Gemini p50 about 1.8 s per call. The slow tail (up to 75 s) came from rate limits and retries; model calls now give up after 60 s and 2 retries (`llm.py`).
- The Gemini free tier allows 500 requests per day. One full run of the 12 journeys used about 250 model calls, and the rerun exhausted the quota: the 429 errors below. A pilot needs a paid tier or a quota alert.
- Groq served 7 calls as the automatic fallback (structured intent and chat); document reading has no fallback because Groq takes no files.
