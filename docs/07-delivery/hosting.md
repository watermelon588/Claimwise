# Hosting the Claimwise demo

The demo runs as four parts:

| Part | Host | Source | Config |
|---|---|---|---|
| Frontend (landing page, case workspace, Mock Console) | Vercel | `frontend/` | [frontend/vercel.json](../../frontend/vercel.json) |
| Agent API | Render web service `claimwise-backend` | `backend/` | [render.yaml](../../render.yaml) |
| Mock providers (insurer, TPA, hospital, bank, grievance) | Render web service `claimwise-mocks` | `mocks/` | render.yaml |
| Connector gateway (consent per case, agent reads) | Render web service `claimwise-connectors` | `connectors/` | render.yaml |

The browser only talks to Vercel. Vercel forwards three paths to Render, so the browser never needs a backend URL or a CORS exception:

- `/api/*` goes to the backend.
- `/mock-api/*` goes to the mocks.
- `/connector-api/api/connectors*` goes to the gateway.

All data is synthetic. Do not upload real medical or insurance records.

## How the connector bearer key works when hosted

Locally, the gateway prints its codes and server bearer key at startup, and you paste the key into the backend's terminal. A hosted service has no terminal, so the values come from environment variables instead:

- **Server bearer key.** The gateway reads `CONNECTOR_AGENT_KEY` from its environment. In `render.yaml`, Render generates this value once on `claimwise-connectors` and copies it into `claimwise-backend`'s `CONNECTOR_AGENT_KEY` (`fromService`). The backend sends it as `Authorization: Bearer ...` on every agent call to the gateway. It never reaches the browser and is never printed.
- **Webhook secret.** `MOCK_WEBHOOK_SECRET` is generated the same way on `claimwise-mocks` and copied into the backend, which uses it to check signed payer webhooks.
- **Demo codes.** The onboarding code and the five provider sign-in codes are generated by Render too (`CONNECTOR_ONBOARDING_CODE`, `CONNECTOR_TPA_CODE`, `CONNECTOR_INSURER_CODE`, `CONNECTOR_HOSPITAL_CODE`, `CONNECTOR_BANK_CODE`, `CONNECTOR_EMAIL_CODE`). You read them in the Render dashboard and type them into **Connect tools**. They stay the same across restarts.
- **Fallback.** Any code that is not set is generated at startup and printed, as before. Values that are set are never printed.

The gateway also accepts its own Render hostname (`RENDER_EXTERNAL_HOSTNAME`, set by Render). It accepts browser requests whose origin is listed in `CONNECTOR_ALLOWED_ORIGINS`, which is your Vercel URL.

## Before you start

- The code is merged to `main` on GitHub.
- A Render account and a Vercel account, both signed in with GitHub.
- A Gemini API key (`GOOGLE_API_KEY`). A second Gemini key (`GOOGLE_API_KEY2`) and a Groq key (`GROQ_API_KEY`) are optional fallbacks.
- Optional: a Neon Postgres connection string (`DATABASE_URL`) so claims survive restarts.
- Choose your Vercel project name now; the steps below assume `claimwise`, giving `https://claimwise.vercel.app`. If that name is taken, use whatever URL Vercel gives you wherever these steps say "Vercel URL".

## Step 1. Create the three Render services

1. Render dashboard, **New**, **Blueprint**. Pick the GitHub repository `Claimwise`, branch `main`. Render finds `render.yaml`.
2. Render asks for the values marked `sync: false`:

   | Service | Key | Value |
   |---|---|---|
   | claimwise-backend | `GOOGLE_API_KEY` | Your Gemini key |
   | claimwise-backend | `GOOGLE_API_KEY2`, `GROQ_API_KEY` | Optional; leave empty if you have none |
   | claimwise-backend | `DATABASE_URL` | Optional Neon string, `postgresql://...?sslmode=require` |
   | claimwise-backend | `CORS_ORIGINS` | `["https://claimwise.vercel.app"]` (JSON list, with the quotes) |
   | claimwise-backend | `CONNECTOR_URL` | `https://claimwise-connectors.onrender.com` |
   | claimwise-mocks | `CLAIMWISE_WEBHOOK_URL` | `https://claimwise-backend.onrender.com/api/webhooks/mock` |
   | claimwise-connectors | `CLAIMWISE_MOCK_URL` | `https://claimwise-mocks.onrender.com` |
   | claimwise-connectors | `CONNECTOR_ALLOWED_ORIGINS` | `https://claimwise.vercel.app` |

3. **Apply**. The first build takes a few minutes per service.
4. Check each service's URL at the top of its page. Render uses `https://<name>.onrender.com` when the name is free, and adds a suffix when it is not (for example `claimwise-backend-x1y2.onrender.com`). If any URL differs from the table:
   - update the matching environment value on Render (**Environment**, edit, **Save, rebuild and deploy**);
   - update the same host in `frontend/vercel.json` and push it to `main`.
5. Check:
   - `https://claimwise-backend.onrender.com/api/health` returns `"status":"ok"`.
   - `https://claimwise-mocks.onrender.com/admin/overview` returns JSON.
   - `https://claimwise-connectors.onrender.com/api/connectors` returns `{"detail":{"code":"VERIFICATION_REQUIRED"}}`. That is the correct answer without a verified case.

## Step 2. Deploy the frontend on Vercel

1. Vercel dashboard, **Add New**, **Project**, import the `Claimwise` repository.
2. **Project name**: `claimwise`. **Root Directory**: `frontend`. Vercel reads `frontend/vercel.json` (Vite, `npm ci`, `npm run build`, output `dist`). Leave the other settings as they are.
3. Environment variables: none are required. `VITE_CLAIMWISE_DEMO_URL` is optional, the URL of a walkthrough video for the landing page.
4. **Deploy**. Open the Vercel URL.
5. If the Vercel URL is not `https://claimwise.vercel.app`, update on Render: `CORS_ORIGINS` (backend) and `CONNECTOR_ALLOWED_ORIGINS` (connectors), then redeploy both.

## Step 3. Smoke test the hosted demo

1. `https://claimwise.vercel.app/api/health` returns the backend's health through the Vercel proxy.
2. `https://claimwise.vercel.app/mocks` opens the Mock Console; **Reset** returns `200`.
3. `https://claimwise.vercel.app/app`: upload `mocks/mock_documents/valid/run1_standard_reimbursement/01_policy_schedule.pdf` and confirm it is read.
4. **Connect tools**. Render dashboard, `claimwise-connectors`, **Environment**: copy `CONNECTOR_ONBOARDING_CODE` into **Workspace verification code**, then `CONNECTOR_TPA_CODE` for **Medivista TPA**.
5. Follow [the demo walkthrough](demo-walkthrough.md) from Run 1. On the hosted demo, skip its "Setup" terminals: Render and Vercel replace them, and the codes come from the Render dashboard.

## Before a live demo

- **Wake the services.** Free Render services sleep after about 15 minutes without traffic, and the first request then waits about a minute. Open the three Render URLs from Step 1.5 a minute before you start. If a page shows a proxy timeout, wait and reload.
- **Mock data resets.** The mock database and generated PDFs live on the service's disk, which is cleared on every restart, deploy or sleep. The mock world starts again from its seed data (clock 2026-10-01). In the Mock Console, **Reset** gives the same clean start on purpose.
- **Connector consent resets.** Verified cases and provider approvals are held in the gateway's memory. After the gateway restarts, verify the case and connect the tools again; the codes stay the same.
- **Claims and uploads.** Without `DATABASE_URL`, claims are in memory and lost when the backend restarts. With Neon, claims survive, but uploaded files are stored on the backend's disk and are lost on restart; the case remembers them, but their previews no longer open.
- **Free-tier hours.** Render's free instance hours are shared by all your free services. Three always-awake services use them about three times faster, so let them sleep between demos.

## Environment reference

| Service | Variable | Required | Purpose |
|---|---|---|---|
| backend | `GOOGLE_API_KEY` | Yes (or Groq) | Gemini, for document reading and replies |
| backend | `GOOGLE_API_KEY2`, `GROQ_API_KEY` | No | Fallback models |
| backend | `LLM_PROVIDER`, `GEMINI_MODEL`, `GROQ_MODEL` | No | Model choice (defaults in `backend/app/config.py`) |
| backend | `DATABASE_URL` | No | Postgres checkpoints; empty means memory |
| backend | `CORS_ORIGINS` | Yes when hosted | JSON list of frontend origins |
| backend | `CONNECTOR_URL` | For connected tools | Gateway URL |
| backend | `CONNECTOR_AGENT_KEY` | For connected tools | Same value as the gateway's |
| backend | `MOCK_WEBHOOK_SECRET` | For live updates | Same value as the mocks' |
| backend | `LANGSMITH_API_KEY`, `TRACE_LOG` | No | Tracing (synthetic data only) |
| mocks | `CLAIMWISE_WEBHOOK_URL` | Yes when hosted | Backend webhook endpoint |
| mocks | `MOCK_WEBHOOK_SECRET` | Yes | Signs webhooks |
| mocks | `MOCK_API_KEYS` | Yes | Keys the gateway and hospital use (`claimwise-demo-key,hospital-demo-key`) |
| connectors | `CLAIMWISE_CONNECTOR_DEMO` | Yes | Must be `1`; the gateway refuses to start otherwise |
| connectors | `CONNECTOR_AGENT_KEY` | Yes when hosted | Server bearer key |
| connectors | `CONNECTOR_ONBOARDING_CODE`, `CONNECTOR_<PROVIDER>_CODE`, `CONNECTOR_EMAIL_CODE` | Yes when hosted | Codes typed in Connect tools |
| connectors | `CLAIMWISE_MOCK_URL` | Yes when hosted | Mock providers URL (local default `http://127.0.0.1:8100`) |
| connectors | `CONNECTOR_ALLOWED_ORIGINS` | Yes when hosted | Frontend origin(s) allowed to post |
| connectors | `CONNECTOR_ALLOWED_HOSTS` | No | Extra hostnames; Render's own is added automatically |
| frontend | `VITE_CLAIMWISE_DEMO_URL` | No | Landing page video |

## Updating the hosted demo

Merging to `main` redeploys all four parts automatically: Vercel and Render both watch the branch. Pull request branches get Vercel preview URLs. Previews call the same Render services, so connector posts from a preview URL are refused unless that preview URL is added to `CONNECTOR_ALLOWED_ORIGINS`.
